# COSIA v0.33 Plan: LLM ToolDraft, ToolCandidate, and Active Registry MVP

## Summary

v0.33 introduces the first zero-base tool acquisition path: LLM `ToolDraft`, normalized `ToolCandidate`, test/approve flow, and a command-adapter active registry MVP.

## Key Decisions

- LLM ToolDraft is untrusted design data.
- `ToolDraft` and `ToolCandidate` are stored separately.
- Draft creation stores the raw draft first, then runs a strict allowlist normalizer.
- Candidate creation can fail without crashing; the draft remains evidence.
- The normalizer may discard, reject, downgrade, redact, or rewrite unsafe fields.
- `ts_module` is draft/review-only and cannot be tested, activated, executed, or exposed in provider schema.
- `command_adapter` MVP uses fixed executable, fixed args, `cwdPolicy=workspace_root`, timeout, output cap, and forced redaction.
- Candidate approval is human approval of design and does not require a passed test.
- Activation requires approved candidate and latest passed test hash matching current candidate content hash.
- Approved candidates are immutable; meaningful changes require a new candidate.
- Candidate content hash excludes ids, timestamps, status, and evidence timestamps.
- Dynamic tool ids must not collide with core, static, reserved, existing active, path-unsafe, whitespace, or command-like ids.

## Public Interfaces

- `cosia tool draft --from-capability <id>`
- `cosia tool candidate review [--all]`
- `cosia tool candidate show <id>`
- `cosia tool candidate test <id>`
- `cosia tool candidate approve <id>`
- `cosia tool activate <candidate-id> --agent <agent-id> --yes`
- `cosia tool active list`
- `cosia tool active show <tool-id>`
- `cosia tool deactivate <tool-id> --reason "<reason>"`
