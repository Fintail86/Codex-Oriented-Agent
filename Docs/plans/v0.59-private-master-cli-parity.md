# COSIA v0.59 Plan: Private Master CLI Parity

## Summary

v0.59 aligns private Telegram master behavior with the local CLI owner surface.

Core rule:
- If a Gateway request is from a private 1:1 chat where the resolved role is `master` and `chatId === userId`, COSIA treats that surface as the remote equivalent of the local CLI owner.

## Key Changes

- `cosia_runtime_command` keeps rejecting CLI strings, slash strings, hash strings, arbitrary argv, unknown args, and secret-like dynamic args.
- In private master direct chat only, `cosia_runtime_command` may execute any cataloged fixed `commandId` through the existing `commandId -> fixed argv -> COSIA CLI` path.
- Non-direct Gateway master contexts, such as groups or chats where `chatId !== userId`, keep the normal Gateway role restrictions.
- Admin and guest behavior is unchanged.
- The CLI command itself still owns its preview, `--yes`, confirmation, policy, and failure behavior.
- The model prompt contract is updated so the LLM treats private master direct chat as CLI-equivalent only when explicitly shown in `GATEWAY COMMAND CONTEXT`.

## Guardrails

- No shell string execution is introduced.
- No natural-language command translator is introduced.
- Command execution remains catalog-driven.
- Dynamic args remain scalar, length-limited, and secret-screened.
- Local CLI/REPL behavior is unchanged.

## Test Plan

- Private master direct chat can execute a normal mutation command.
- Private master direct chat can execute a system-boundary command through fixed argv.
- Private master direct chat can execute a dangerous command through fixed argv.
- Non-direct Gateway master remains blocked from system-boundary model-facing command execution.
- Gateway admin remains read-only.
- Gateway guest remains blocked.
- CLI strings remain blocked.
- Existing Gateway, memory/skill, runtime command, and policy tests remain passing.
