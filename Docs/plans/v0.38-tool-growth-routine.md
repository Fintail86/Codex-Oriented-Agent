# COSIA v0.38 Plan: Tool Growth Routine

## Summary

v0.38의 목표는 v0.31-v0.37의 capability/tool acquisition 부품을 하나의 Tool Growth Routine으로 묶는 것이다. 사용자는 여러 CLI 단계를 직접 이어 붙이지 않고도 후보 생성, 검토, 테스트, 명시 승인 후 active 등록까지 진행할 수 있다.

핵심 원칙:

- 버전은 `0.38.0`.
- 새 tool acquisition 엔진을 만들지 않고 기존 `CapabilityPlanner`, `ToolAcquisitionManager`, activation hardening을 orchestration한다.
- 자동 생성은 `ToolDraft` / `ToolCandidate`까지만 허용한다.
- `tool grow --request`는 shell approval, command execution, active registration을 만들지 않는다.
- active tool 등록은 계속 명시 승인 필요다.
- 실패/거절/취소 후보는 hard delete 없이 evidence-preserving 상태로 남긴다.
- CLI + REPL이 v0.38 범위다.
- 일반 `runSession()` 자연어 프롬프트는 routine을 자동 시작하거나 active tool을 자동 생성/등록하지 않는다.

## Tool Growth Routine

```ts
type ToolGrowthRoutine = {
  id: string;
  sourceRequest: string;
  sourceScanId?: string;
  sourceCapabilityId?: string;
  draftIds: string[];
  candidateIds: string[];
  selectedCandidateId?: string;
  targetAgentId?: string;
  providerId?: string;
  status:
    | "candidate_ready"
    | "test_passed"
    | "test_failed"
    | "awaiting_activation"
    | "activated"
    | "rejected"
    | "cancelled";
  attemptCount: number;
  evidence: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
  completedAt?: string;
  reason?: string;
};
```

`tool grow --request` flow:

```text
scan -> proposal -> LLM draft -> normalized candidate -> routine record
```

Rules:

- Runs capability scan for the request.
- Creates capability proposal from the fresh scan.
- Runs ToolDraft generation through existing `ToolAcquisitionManager`.
- Runs existing normalizer and creates ToolCandidate if possible.
- Records a ToolGrowthRoutine linked to scan/proposal/draft/candidate ids.
- Creates no shell approval.
- Executes no command.
- Creates no active tool.
- Candidate remains non-model-facing until activation.

## Public Interfaces

```text
cosia tool grow --request "<text>" [--agent <agent-id>] [--provider <provider>]
cosia tool grow review [--all]
cosia tool grow show <routine-id>
cosia tool grow test <routine-id> --yes
cosia tool grow activate <routine-id> --agent <agent-id> --yes
cosia tool grow reject <routine-id> --reason "<reason>"
cosia tool grow retry <routine-id> [--provider <provider>]
cosia tool grow cancel <routine-id> --reason "<reason>"
```

REPL commands:

```text
/tool grow <request>
/tool grow show [routine-id]
/tool grow test [routine-id] --yes
/tool grow activate [routine-id] --agent <agent-id> --yes
/tool grow reject [routine-id] --reason "<reason>"
/tool grow retry [routine-id]
/tool grow cancel [routine-id] --reason "<reason>"
```

Natural hash command mappings:

```text
#도구 성장 <request>
#이 도구 테스트해
#이 도구 활성화해
#이건 내가 원한 기능이 아니야 이유는 <reason>
#다른 도구 후보 만들어줘
#도구 생성 취소
```

## Behavior

- `tool grow test <id> --yes` uses the existing candidate test path and does not approve or activate automatically.
- `tool grow activate <id> --agent <agent-id> --yes` may approve candidate design as part of the explicit activation command, then uses the existing hardened activation path.
- `reject` marks the current selected candidate rejected/discarded with reason and keeps evidence.
- `retry` appends a new draft/candidate attempt to the existing routine and links previous rejection evidence.
- `cancel` stops the routine and rejects/discards the current pending candidate without deleting evidence.
- REPL `currentToolGrowthRoutineId` is convenience state only; explicit routine id wins.

## Test Plan

- `tool grow --request` creates scan, capability proposal, ToolDraft, ToolCandidate, and ToolGrowthRoutine.
- `tool grow --request` does not create shell approval, execute command, or create active tool.
- generated candidate remains non-model-facing until activation.
- routine records source scan id, capability id, draft id, candidate id, request, provider, and attempt count.
- routine start handles candidate normalization failure by storing draft and routine evidence without crashing.
- `tool grow test <id>` without `--yes` refuses execution.
- `tool grow test <id> --yes` executes candidate test and updates routine status.
- `tool grow activate <id> --agent <agent-id>` without `--yes` does not mutate.
- `tool grow activate <id> --agent <agent-id> --yes` approves candidate if needed and activates through existing activation path.
- `reject` preserves candidate evidence and hides it from default routine review.
- `retry` appends a new draft/candidate attempt to the same routine.
- `cancel` marks routine cancelled and prevents further test/activate.
- REPL slash/hash commands operate on current routine id only when unambiguous.
- ordinary non-hash `runSession()` prompts do not auto-create routines or active tools.

## Assumptions

- The “initial tool” in UX means `ToolCandidate`, not active executable tool.
- CLI + REPL are in scope; general `runSession()` automatic routine startup is out of scope.
- Active registration always requires explicit user approval.
- `grow activate --yes` may approve candidate design and activate in one explicit command.
- Failed candidates are preserved as evidence, not hard-deleted.
