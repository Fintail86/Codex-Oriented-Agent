# v0.42 Provider Onboarding And OAuth

## Goal

Make provider setup a first-class replaceable-brain onboarding flow and prepare COSIA-owned OAuth support.

## Why This Stage Exists

COSIA's direction depends on provider-neutral brains. Users should not need to know scattered provider ids, auth flags, or external CLI assumptions before connecting a provider.

## Current State

- Provider profiles are the intended model selection path.
- `codex-cli` can be added as an OAuth profile, but current OAuth behavior delegates to an external CLI.
- API key and env-based provider setup exist through direct flags.
- Gateway/Telegram connector setup is separate and must remain separate.

## Intended End State

- Provider onboarding is guided and scriptable.
- Supported providers are listed without implying a default.
- Provider-specific setup handlers own required fields, secret prompts, auth checks, and recovery hints.
- COSIA-owned OAuth is defined as a provider-auth boundary, with external CLI delegation treated as compatibility.

## In Scope

- Provider onboarding registry design.
- Guided provider setup CLI.
- Scriptable provider profile commands routed through provider-specific validators.
- Secret storage rules for API keys and future OAuth tokens.
- Codex OAuth boundary design and first implementation slice if feasible.

## Out Of Scope

- Making any provider the default.
- Moving provider selection into gateway or connector config.
- Storing secrets in public runtime config.
- Implementing unverified OAuth endpoints from memory.
- Removing external CLI delegation before COSIA-owned OAuth is ready.

## Implementation Plan

- Define provider onboarding descriptors:
  - provider id
  - display name
  - supported auth modes
  - required fields
  - secret handling
  - check behavior
  - setup hints
- Add a guided provider setup command that lists supported providers and asks for required fields.
- Keep direct `provider profile add` commands working for scripts.
- Route both guided and direct paths through the same validation/secret handling.
- For OAuth, introduce a provider-auth boundary that can support browser/device flow, token refresh, and private token storage.
- Keep current `codex-cli` external delegation as compatibility until COSIA-owned OAuth is implemented and verified.

## Public UX / CLI Impact

- Add a guided provider setup path.
- Existing provider profile commands remain valid.
- Missing provider errors should point to guided and scriptable setup paths.
- Provider profile list/show/check must never print secrets.

## Data / Config / Policy Impact

- Provider profiles remain in runtime private config.
- API keys and future OAuth tokens remain in private secret storage.
- Public defaults do not include active provider profiles.
- No gateway connector stores provider profile or provider id.

## Risks And Guardrails

- Do not reintroduce `codex-cli` as a default provider.
- Do not make OAuth tokens visible in logs, status, check output, audit, evidence, or docs.
- Do not make provider onboarding interactive-only; scriptable paths must remain.
- Verify OAuth details against official provider docs before implementation.

## Test Plan

- Fresh init has no active provider.
- Guided setup lists providers without auto-selecting one.
- Scriptable and guided setup produce equivalent provider profiles.
- API key setup uses hidden input and private secret storage.
- Env setup stores only env var name.
- OAuth setup stores no token unless COSIA-owned OAuth flow explicitly succeeds.
- Gateway start uses active provider profile and not connector provider settings.

## Acceptance Criteria

- Provider onboarding is centralized.
- Provider and connector setup remain separate.
- Codex OAuth is no longer treated as a hidden hardcoded runtime default.
- Existing provider tests pass.

## Follow-Up Work

- Provider A/B comparison and provider capability scoring can build on this boundary later.
