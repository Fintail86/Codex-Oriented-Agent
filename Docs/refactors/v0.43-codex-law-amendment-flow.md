# v0.43 Codex Law Amendment Flow

## Goal

Treat protected `codex/*` source changes as governed Codex law amendments rather than ordinary file writes.

## Why This Stage Exists

The Codex law is COSIA's operating constitution. If these files are changed through generic file writing, approval state can become confusing, especially through Telegram or other connectors.

## Current State

- Protected Codex paths cannot be modified through generic `write_file`.
- The agent may still propose changes in conversation.
- Telegram approval UX has shown that conversational approval is not enough unless connected to runtime approval state.
- STYLE and agent-related files can affect behavior but are not part of the v0.43 Codex-only amendment scope.

## Intended End State

- Codex law changes have a dedicated preview/apply/check flow.
- Ordinary `write_file` remains separate from Codex amendment.
- Telegram and REPL approval for Codex-risk changes routes through runtime approval state.
- The user can inspect, approve, reject, pause, or revise proposed amendments.
- Agent behavior files such as `agents/*/STYLE.md` continue to use the existing overwrite approval path until a later behavior-file amendment flow exists.

## In Scope

- Codex law amendment command design.
- Amendment preview and apply flow.
- Protected Codex path handling.
- Runtime approval state for Codex amendment.
- Documentation explaining Codex law vs ordinary files.

## Out Of Scope

- Broad policy language redesign.
- Removing protected path enforcement.
- Allowing generic `write_file` to modify protected Codex paths.
- Automatic Codex amendment from ordinary conversation without preview.
- Agent STYLE/AGENT/LOCAL_RULES amendment flow.

## Implementation Plan

- Add a Codex law command group design:
  - `cosia codex show`
  - `cosia codex check`
  - `cosia codex amendment propose --path <path> --content-file <file> --reason "<reason>"`
  - `cosia codex amendment apply <id> --yes`
  - `cosia codex amendment reject <id> --reason "<reason>"`
  - `cosia codex amendment cancel <id> --reason "<reason>"`
- Define amendment records with target path, previous hash, proposed content or patch, reason, status, and approval metadata.
- Route protected Codex write attempts to amendment preview guidance.
- Make Telegram `#적용` apply only a concrete pending runtime approval, not plain conversational agreement.
- Reject direct amendment proposals for generated mirrors such as `codex/POLICY.md`; amend `codex/POLICY.json` and regenerate mirrors instead.
- Keep STYLE-like behavior-affecting files out of v0.43 even when they affect runtime behavior.

## Public UX / CLI Impact

- Users get explicit Codex amendment previews.
- Generic overwrite approval does not apply to protected Codex law paths.
- Telegram says what approval command is required and whether the file has actually changed.

## Data / Config / Policy Impact

- May add amendment ledger storage.
- Must preserve previous hashes for freshness checks.
- Policy protected paths remain deterministic.

## Risks And Guardrails

- Do not let LLM claims substitute for runtime amendment state.
- Do not weaken protected path enforcement.
- Do not hide Codex law mutations inside ordinary file edits.
- Do not store secrets in amendment records.

## Test Plan

- Generic `write_file` to protected Codex path is denied or redirected to amendment guidance.
- Amendment preview does not mutate files.
- Amendment apply requires explicit approval.
- Stale hash blocks apply.
- Telegram conversational approval alone does not apply amendment.
- Successful apply updates target file and records evidence.

## Acceptance Criteria

- Codex law has a dedicated mutation path.
- The runtime can truthfully state whether a Codex file was changed.
- Protected Codex changes are previewed, approved, and auditable.

## Follow-Up Work

- Codex amendment UX can later support diffs, rollback, and amendment history browsing.
