# v0.46 Tool Growth Surface Slimming

## Goal

Keep COSIA's tool-growth internals, but expose them through a lighter guided UX instead of forcing users to manage every internal state.

## Why This Stage Exists

Tool growth is one of COSIA's differentiators, but the internal sequence can become a configuration maze if exposed directly:

```text
scan -> proposal -> draft -> candidate -> test -> approve -> activate
```

## Current State

- Capability proposal, ToolDraft, ToolCandidate, active tool, and learned blueprint concepts exist.
- Tool growth routine can orchestrate parts of the flow.
- Normal UX exposed source proposal, draft, and candidate ids too early.

## Intended End State

- Normal UX asks whether a repeated action should become a governed capability.
- `tool grow` is the normal guided path.
- `tool grow show/review --advanced` and direct candidate/draft commands remain available for review, debugging, and governance.
- Executable activation remains explicitly approved.
- Failed/rejected/cancelled attempts remain preserved as evidence.

## In Scope

- Tool growth guided UX wording.
- Normal vs advanced command visibility.
- Candidate/rejection/evidence review UX.
- Evidence lifecycle direction for tool growth artifacts.
- Documentation of active executable approval gates.

## Out Of Scope

- Silent active tool registration.
- `ts_module` execution.
- Arbitrary shell automation.
- Removing internal candidate/test/approval states.
- Hard-deleting failed candidates by default.

## Implementation Plan

- Make normal `tool grow --request` output routine-centric:
  - routine id
  - source request
  - candidate readiness
  - routine status
  - next command
- Hide source scan/proposal/draft/candidate ids from default start/show/review output.
- Add `--advanced` to `tool grow show`, `tool grow review`, and related CLI output paths for source ids, selected candidate id, candidate detail, and evidence keys.
- Keep direct candidate/active/blueprint commands for advanced users and scriptable governance.
- Keep REPL/Telegram tool growth responses on the same normal formatter by default.
- Add evidence lifecycle language to docs and output wording:
  - active evidence
  - closed evidence
  - archived evidence
  - compacted summaries
  - explicit purge for user-requested cleanup
- Do not implement archive/compact/purge storage in this stage.

## Public UX / CLI Impact

- Normal UX becomes less state-machine heavy.
- Advanced commands remain scriptable.
- Activation still requires explicit approval and latest passed test.
- `tool grow show <id>` defaults to normal summary.
- `tool grow show <id> --advanced` exposes internal ids and candidate detail.
- `tool grow review --all --advanced` exposes closed routines and evidence summaries.

## Data / Config / Policy Impact

- No required schema change for the first slimming pass.
- Future evidence lifecycle may add archive/compact metadata.
- Active tool records and approval evidence remain preserved.
- No stored routine record shape changes are required.

## Risks And Guardrails

- Do not hide risk details behind friendly wording.
- Do not auto-activate executable tools.
- Do not remove audit/evidence just to simplify UX.
- Do not let tool growth bypass provider/policy/connector boundaries.

## Test Plan

- `tool grow --request` still creates non-model-facing candidates only.
- Default `tool grow --request` output does not expose source proposal/draft/candidate ids.
- `tool grow show` defaults to normal summary.
- `tool grow show --advanced` exposes source ids and selected candidate details.
- `tool grow review --all --advanced` exposes closed routines and evidence keys.
- Testing requires explicit `--yes`.
- Activation requires explicit `--yes` and existing activation hardening.
- Rejected/cancelled candidates remain visible with advanced/all views.
- Normal output is concise but includes next actions.

## Acceptance Criteria

- Normal tool-growth UX is understandable without knowing every internal state.
- Advanced state inspection remains available.
- Executable activation stays approval-gated.
- Evidence is preserved without becoming normal UX clutter.

## Follow-Up Work

- Learned blueprint UX and evidence cold storage can be refined after normal tool growth is simpler.
